## 11. Zero-copy investigation — closed, root cause fully identified

Trigger: user requested confirmation that camera frames stay on the dGPU's silicon throughout VA-API encode/decode, given debayer and encode were both pinned to the dGPU via `DRI_PRIME`/render-node targeting.
Initial direct test (`gst-launch-1.0 -v ... | grep caps`) showed `pipewiresrc` and `libcamerasrc` BOTH negotiate plain `video/x-raw` (system memory) with the PipeWire libcamera node, no DMABuf/VAMemory caps feature — appeared to rule out zero-copy via either GStreamer camera source.
Lead: a WebRTC/Firefox upstream commit ("Video capture PipeWire: add support for DMABuf buffer type", webrtc-review.googlesource.com/c/src/+/338921, Firefox bug 1876895) explicitly states DMABufs WERE already in use by `pipewiresrc` in the scenario that motivated that fix — directly contradicting the "ruled out" conclusion above. Reopened the investigation on this basis.
Deeper `GST_DEBUG` capture (`va*:6`, later adding the `pipewirepool`/`pipewiresrc` categories after discovering the correct category names via `gst-launch-1.0 --gst-debug-help`) revealed `vapostproc` DOES actively attempt real DMA-BUF export from camera frames (`gst_va_base_transform_propose_allocation` proposing a VA-backed pool upstream; `_va_create_surface_and_export_to_dmabuf` actually invoked) — confirming the capability is real and exercised, not absent.
ROOT CAUSE, confirmed directly: the export attempt fails inside the `iHD` driver (26.2.4) itself — `_va_create_surface_and_export_to_dmabuf: Different fourcc: requested BGRA - returned ARGB` / `requested RGBX - returned XBGR`, followed by `vaExportSurfaceHandle: invalid VASurfaceID`. The driver returns a VA surface in a different channel-ordering than requested, and the subsequent export call fails against that mismatched surface. This is a genuine driver-level bug in RGBA-family DMA-BUF surface export, not a pipeline or config error — reproduces on every run, before the pipeline even reaches PAUSED, independent of pipeline structure.
Failure is silent to the end user: GStreamer falls back to a system-memory pool automatically after the failed export, so the pipeline always runs and produces correct video — the RAM round-trip was invisible without this specific targeted debug capture.
Workaround attempted: request `format=NV12` directly at the `pipewiresrc` caps filter, to route around the buggy RGBA export path entirely (NV12 never appeared in either failing fourcc line). FAILED — confirmed via full log capture: `pipewiresrc`'s camera node only ever advertises `RGBA` in its fixed resolution/format list (per §3's earlier finding); requesting NV12 upstream of it fails with the same `no more input formats`/`not-negotiated` error as any other unsupported format request. No workaround available at the GStreamer pipeline level.
CONCLUSION: true zero-copy (camera capture through VA-API encode without a RAM round-trip) is NOT achievable today via either `pipewiresrc` or `libcamerasrc`, on this driver version, regardless of which physical GPU debayer/encode are pinned to. The only remaining path is custom code against libcamera's C++ API (consuming DMA-BUF fds directly from completed `Request`/`FrameBuffer` objects) and libva's DRM-PRIME external-buffer import — bypassing GStreamer's camera-source elements entirely. Not started this session; a real, separate undertaking if pursued.

ADDENDUM — investigated whether libcamera could output NV12 directly (avoiding the RGB32 code path that hits the driver bug above) instead of pursuing Option B:
- `DebayerEGL::getOutputConfig()` (GPU path) is hardcoded to exactly four 32-bit RGB variants (`XRGB8888`/`ARGB8888`/`XBGR8888`/`ABGR8888`) — anything else returns `-EINVAL`. Confirmed directly from source.
- `DebayerCpu`'s multi-year patch history (Hans de Goede, Red Hat) shows every format-extension patch adding only additional RGB variants (`RGB888` → `BGR888`) — no patch found adding YUV420/NV12 output at any point.
- CONCLUSION: libcamera's software ISP is RGB-output-only architecturally, on BOTH debayer backends, today. This is not "GPU behind CPU" — it's a subsystem-wide gap. Confirmed via upstream patch series "Add GLES 2.0 GPUISP to libcamera" (Bryan O'Donoghue, Linaro) whose own commit message states outright: "we don't have full feature parity with CPUISP just yet on pixel format output" — this GPU-ISP feature itself only formally merged upstream ~Jan 2026, very recent relative to this session.
- Even if NV12 output were added to libcamera, PipeWire's libcamera SPA plugin (a SEPARATE upstream project) would ALSO need changes — it currently only ever advertises RGBA in its fixed format list (§3). Real NV12-through-libcamera would require coordinated changes across two upstream projects, for a feature that exists in neither today.
- RECOMMENDATION: Option B (custom code against libcamera's C++ API + libva DRM-PRIME import, bypassing GStreamer's camera-source layer) is the narrower-scoped path — it requires fixing/working around ONE already-identified bug in ONE project (the `iHD`/`gst-plugins-bad` RGB32 DMA-BUF export mismatch above), rather than new feature development spanning two upstream projects. libcamera already produces DMA-BUF-backed RGBA natively; the blocker is getting that handed cleanly into a VA surface, which is exactly the fault already isolated. If zero-copy is pursued further, start here rather than with NV12-in-libcamera.

FURTHER INVESTIGATION (extended session) — GL bridge and libcamerasrc allocator internals:
- Tested `glupload`/`glcolorconvert` as a possible bridge between camera source and `vapostproc`, on the theory that Mesa's GL-based DMA-BUF export (mature, used daily for Wayland compositing) might avoid the `iHD` export bug entirely. RESULT: dead end — `glcolorconvert`'s SRC pad template and `vapostproc`'s SINK template do not intersect for DMA-BUF caps as declared; static link rejection (`could not link glcolorconvertelement0 to varenderd129postproc0`) regardless of caps-string syntax attempted (tried bare `memory:DMABuf`, `format=DMA_DRM`, `format=DMA_DRM,drm-format=NV12:...`, and no caps filter at all — all four failed identically at pre-link template comparison, ruling out syntax as the cause).
- Examined `gstlibcameraallocator.cpp` source directly (Nicolas Dufresne, Collabora, 2020): `GstLibcameraAllocator` is declared `G_DEFINE_TYPE(GstLibcameraAllocator, gst_libcamera_allocator, GST_TYPE_DMABUF_ALLOCATOR)` — libcamerasrc's internal buffer allocator IS a real `GstDmaBufAllocator` by inheritance. This reopened the investigation: if the allocator is genuinely DMA-BUF-backed, the RGBA-only caps found earlier might reflect the mappable-buffer caps convention (no explicit memory-feature tag required for mappable DMA-BUF, per GStreamer's own documented convention — same pattern seen on `vapostproc`'s own output pool `vapool1` early in this investigation) rather than proof of a system-memory copy.
- DECISIVE TEST: explicitly requested `video/x-raw(memory:DMABuf),format=DMA_DRM` directly from `libcamerasrc` (no intermediate elements). RESULT: immediate static-template rejection — `WARNING: erroneous pipeline: could not link libcamerasrc0 to varenderd129postproc0, libcamerasrc0 can't handle caps video/x-raw(memory:DMABuf)...`. This is definitive, not inferred: `libcamerasrc`'s public SRC pad template genuinely never advertises the DMA-BUF caps feature in any format, confirmed via GStreamer's own static caps-template check (fires before any live negotiation attempt).
- RECONCILED CONCLUSION: `GstLibcameraAllocator`'s DMA-BUF-capable internal memory management and `libcamerasrc`'s external pad-template capability advertisement are two separate layers in GStreamer's design — the allocator can produce DMA-BUF-backed `GstMemory`, but the element surrounding it was never wired to offer that memory type to downstream consumers via caps negotiation. This is the actual, precisely-located gap: not a driver bug (that's `vapostproc`'s separate, already-documented export failure above), not a PipeWire limitation, not a caps-syntax issue — a specific, narrow omission in `libcamerasrc`'s own caps/negotiation code, upstream in libcamera itself.
- RECOMMENDATION (supersedes the earlier Option B framing as the default next step): patch `libcamerasrc`'s SRC pad template and negotiation logic (`src/gstreamer/gstlibcamerasrc.cpp`, likely also `gstlibcameraallocator.cpp`/`.h`) to expose the `memory:DMABuf` caps feature the allocator already supports internally. This is a smaller, more targeted fix than Option B's from-scratch custom application, and sits in the same upstream project already being locally patched this whole session (existing local overlay: `agc.h.patch`, `agc.cpp.patch`, `egl-r16-import.patch`, `bayer-r10p-scale-fix.patch`) — same workflow, one more file.
